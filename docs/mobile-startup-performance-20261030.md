## 已确认的等待链路

```text
启动 / 加载 APK 内 WebView 资源
  → 从安全存储取得 refresh token
  → 等待 /api/auth/refresh
  → 挂载 Vue / 进入首页
  → 请求 courses；同时读取或刷新 semester
  → 课程、学期均可用后生成“接下来的课程”
  → 卡片进场动画
```

1. `frontend/src/main.ts:56` 在 `app.mount` 之前等待 `restoreSession()`。启动画面能显示，但课程界面必须等会话网络请求。`frontend/src/api/request.ts:57` 的请求配置超时为 10 秒；弱网时启动提示可能长时间停留，原生实际超时还需实机验证。
2. `frontend/src/stores/courses.ts:17` 每次进程启动都从空数组、`loaded=false` 开始，只有内存缓存。`HomePage.vue:53` 又要求课程和学期均已就绪，因此即使学期有缓存，课程仍阻塞卡片。
3. `frontend/src/stores/semester.ts:15` 已实现按账号保存学期设置并后台刷新，可借用其思路，但课程还需要支持补课、停课与日期作息规则，不能只保存当前一张卡片。
4. `frontend/src/components/ReminderRuntime.vue:65` 在账号变化时清空课程。新缓存接入必须同步调整此处，否则恢复的课程可能立即被清掉；账号切换隔离仍需保留。
5. `HomePage.vue:427` 的卡片动画为 680 ms，另延迟 76 ms。它不是接口耗时，但从插入到动画完成需约 756 ms，会影响课程立即可读的感受。

已有优化需要保留：课程与学期请求已并行，进行中的课程请求已合并；建筑请求不会阻塞课程卡，地图已有可视区域延迟加载；refresh 成功直接携带用户信息，正常恢复不必再请求 `/auth/me`；字体已有 `font-display: swap`。继续简单叠加“请求并行”或“地图 lazy”不会解决前两项。

## 分阶段改进

### P0：课程先显示，网络后台同步

- 增加按账号保存的启动快照：课程、学期起始日期、周数、日期作息规则、补课/停课信息、快照版本和同步时间。采用一份一致的快照，校验成功后整体替换；避免一半新课表、一半旧学期设置。
- 启动先挂载轻量界面，读取与本机既有会话绑定的账号及其快照，立即计算并展示下一门课；会话恢复在后台进行。单独定义“仅本地可读”状态，不能把缓存存在直接当作在线鉴权通过。聊天室、写入等仍等待有效会话。
- 保留 access token 仅在内存、refresh token 在 Android 安全存储的现有设计。身份失效明确返回 401 时退出本地展示并清理相应缓存；超时、断网和 5xx 则保留本机课表，标明上次同步时间，提供重试。
- 登出、注销、切换账号时清理或隔离相应快照和 store，阻止旧账号迟到的请求写回。用请求代次和账号标识检查响应归属；会话恢复保持单次并发，避免轮换 refresh token 时产生重复请求。
- 沿用现有校园时间和课程实例化函数，每次启动、跨分钟、跨日、返回前台重新计算；不持久化“当前教学周”或固定的下一门课结果。编辑、导入、补课、学期调整成功后更新一致快照；网络刷新失败不能把已有课表显示成“没有课程”。
- 首次安装/首次登录没有缓存时显示骨架和准确状态，联网取得数据后建立快照。离线快照只能代表上次同步结果，不能获知其他设备刚修改的课程。

改动集中在 `main.ts`、`App.vue`、`auth.ts`、`sessionTokens.ts`、`router/index.ts`、`courses.ts`、`semester.ts`、`ReminderRuntime.vue` 和 `HomePage.vue`。仅给 courses 增加持久化、不调整启动会话阻塞，仍会先等公网 refresh。

这种读取本地数据、网络更新后驱动 UI 的方式符合 [Android 官方离线优先架构](https://developer.android.com/topic/architecture/data-layer/offline-first)。本项目第一阶段可用经过严格校验的小型本地快照；数据量增长后再评估 IndexedDB 或原生数据库。

### P1：减少在线首次加载的往返

为新客户端的登录/refresh 增加可选的启动数据返回，在同一次成功认证响应中携带一致的课程和学期快照，旧客户端行为保持兼容。以当前约 10.8 KB 的课程数据量，值得验证用少量响应体换掉后续网络阶段的收益。首页和提醒运行时复用此结果，避免再立即发一轮重复请求；业务快照读取失败时应允许认证成功，并回退到独立加载。

只新增一个“refresh 之后调用”的 `/bootstrap`，虽然可以合并 courses/semester，但这两个请求原本就并行，不能据此承诺省掉整轮串行等待。应以真实网络瀑布判断收益。

### P1：让课程内容立即可读

课程主卡取消从透明开始的长动画，或缩短到 100–150 ms 并立即展示文字。卡片首次绘制后再启动建筑搜索数据刷新、地图初始化、自动定位以及较重的通知重算。已有系统通知继续有效；同步任务需保证随后执行，不能因延后首屏工作漏掉提醒更新。

地图目前虽按可见性延后初始化，组件仍静态导入。可以评估异步组件，将组件代码也拆到需要时加载；按 [Vue 官方性能指南](https://vuejs.org/guide/best-practices/performance) 核查依赖和构建产物。原生 APK 的 JS/CSS/字体为本地资源，不能把字体包总大小直接当成公网下载瓶颈。

### P2：根据手机数据改善在线链路

为原生请求补充阶段耗时，确认连接复用、TLS 建连、refresh 服务时间和隧道延迟。当前连接复用样本明显更快，但没有证据表明现有 Android 请求栈未复用连接。先实测，再决定是否调整请求调度或评估更近的后端部署位置。

当前样本没有支持优先上 Redis、换数据库或堆 worker 的证据。课表查询已经是毫秒级，优先消除课程展示对公网的依赖，收益更直接。
