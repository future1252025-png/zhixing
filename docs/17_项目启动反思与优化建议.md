# 17_项目启动反思与优化建议：项目启动反思与优化建议

## 1. 当前状态判断

当前文件夹是一套项目启动文档包，代码项目尚未创建。文档已经覆盖了项目概述、需求、MVP、架构、数据库、接口、前后端任务、测试、部署和 AI 编程提示词。

整体方向清晰：先做一个面向湖北大学学生的 Web MVP，验证核心闭环：

```text
登录 -> 校园地图 -> 建筑详情 -> 建筑聊天室 -> 定位发言 -> 课程表 -> 出发建议
```

但从初期落地角度看，现有范围仍然偏大。如果一开始就同时做 WebSocket、管理员后台、举报、提醒、多频道、关键词影响日程等功能，容易拖慢第一个可运行版本。

## 2. 第一轮反思

### 2.1 MVP 应再收窄

现有 MVP 中 P0 功能包括认证、地图、建筑、聊天、定位、课程、日程，已经足够形成闭环。建议第一阶段只完成这些功能的最小可运行版本：

```text
用户注册登录
建筑列表与详情
地图点位展示
单建筑单聊天室
发送消息时后端定位校验
课程 CRUD
下一节课出发建议
```

以下功能建议延后到第二阶段：

```text
建筑内多频道
WebSocket 实时聊天
举报处理
管理员完整后台
提醒功能
关键词影响缓冲时间
```

原因：这些功能有价值，但不是验证核心产品是否成立的必要条件。

### 2.2 技术风险需要提前处理

浏览器定位有两个关键限制：

1. 用户必须授权定位。
2. 正式环境通常需要 HTTPS 才能稳定使用 Geolocation API。

因此项目初期应准备一个“模拟定位模式”，方便本地开发和演示：

```text
开发环境允许手动输入或选择用户坐标
生产环境优先使用浏览器真实定位
```

这样可以避免开发时被定位权限、设备环境、校园外测试条件卡住。

### 2.3 管理员功能定义存在轻微冲突

`04_第一版MVP范围.md` 中管理员和举报是 P1，但 `15_验收标准.md` 中“管理员隐藏消息”被标为必须。

建议调整为：

```text
第一阶段必须：后端提供隐藏消息接口，并准备一个默认管理员账号
第一阶段可选：完整管理员页面
```

这样既满足验收，又不会把前端后台页面做得过重。

### 2.4 聊天实现建议分两步

文档中同时设计了 HTTP 消息接口和 WebSocket 聊天。对初期来说，建议分阶段：

```text
第一阶段：HTTP 拉取消息 + HTTP 发送消息
第二阶段：加入 WebSocket 实时广播
```

这样可以先保证消息保存、匿名显示、定位校验、敏感词过滤等核心规则正确，再增强实时体验。

### 2.5 建筑数据是启动前关键资产

项目需要一批湖北大学主要建筑的初始数据，包括：

```text
建筑名称
建筑类型
简介
经纬度
允许发言半径
地图 x/y 百分比坐标
```

当前文档只列出了建筑名称，尚缺真实坐标和地图点位。建议启动前单独建立 `seed_buildings.json` 或 `seed_buildings.py`，先用 8 到 12 个建筑完成演示闭环。

## 3. 建议优化后的第一版范围

### 3.1 第一阶段必做

```text
后端 FastAPI 项目初始化
SQLite 数据库与 SQLAlchemy 模型
用户注册、登录、JWT
建筑列表、建筑详情、建筑种子数据
HTTP 消息列表、HTTP 发送消息
发送消息时定位校验
课程增删改查
下一节课识别与出发时间建议
前端登录、注册、地图、建筑详情、聊天室、课程表、日程建议页面
基础响应式布局，优先手机端
```

### 3.2 第一阶段只做简化版

```text
管理员：只做默认管理员账号和隐藏消息接口
聊天：先不做 WebSocket，只做手动刷新或进入页面加载
地图：先用静态卡通底图或简化校园示意图
定位：支持真实定位，也支持开发模拟坐标
提醒：先显示建议出发时间，不做系统通知
```

### 3.3 第一阶段暂缓

```text
完整管理员后台
举报工作流
多频道聊天室
WebSocket 实时聊天
关键词动态缓冲
消息频率限制的复杂实现
真实校园统一身份认证
教务课表导入
```

## 6. 下一步建议

如果现在开始开发，建议不要先做完整前端，也不要先做 WebSocket。最稳的起点是：

```text
先创建 campusmind/backend，完成 FastAPI + SQLite + 用户/建筑/课程/消息模型。
```

只要后端模型和基础接口跑通，后面的前端页面、地图点位和日程建议都会更容易迭代。
