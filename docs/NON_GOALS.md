# 智行 CampusMind 第一版不做的功能及原因

## 1. 文档目的

本文件明确第一版不做什么，避免开发过程中范围失控。未进入第一版的功能可以写入课程设计文档的“后续扩展”部分，但不应阻塞 MVP 完成。

## 2. 不做清单

| 功能 | 第一版不做原因 | 后续扩展方向 |
|---|---|---|
| WebSocket 实时聊天 | 联调、断线重连、状态同步复杂 | 主流程完成后升级留言区 |
| 多频道聊天室 | 增加频道表、页面和路由复杂度 | 建筑留言稳定后再扩展 |
| 完整管理员后台 | 对学生主流程帮助不大 | 后续做建筑和留言管理 |
| 举报审核流程 | 依赖后台管理闭环 | 可作为内容治理模块 |
| 真实地图 SDK | 申请、坐标适配和样式成本高 | 后续接高德/腾讯地图 |
| 室内定位 | 技术难度高，GPS 精度不足 | 后续结合蓝牙或 Wi-Fi |
| 学校统一身份认证 | 接入权限和流程不可控 | 后续对接校园认证 |
| 真实 AI 大模型 API | 账号、费用、稳定性和调试风险高 | 预留 AI 建议入口 |
| 自动导入教务课表 | 需要教务系统接口 | 后续做导入或 OCR |
| 推送通知 | 浏览器权限、HTTPS 和兼容性复杂 | 后续做 PWA 通知 |
| 原生 Android/iOS | 开发量大 | H5/PWA 稳定后再考虑 |

## 3. 保留为文档亮点的方式

这些功能虽然第一版不做，但可以在课程设计文档中作为系统扩展性说明：

1. 技术架构预留模块边界。
2. 数据库设计说明后续可增加表。
3. 接口设计说明后续可扩展接口。
4. 项目总结中说明为何第一版做范围收敛。

## 4. 范围控制规则

如果某个新功能不能直接服务以下主流程，就不进入第一版：

```text
登录 -> 建筑 -> 留言 -> 课程表 -> 下一节课 -> 出发建议
```
